What this is

Honey Chain is an MVP of a beekeeping management and honey traceability system. A beekeeper registers an apiary and its hives, harvests a batch, and records it moving through processing and quality verification. An admin approves the quality check and packages the batch, which mints a QR code. Anyone who scans that QR lands on a public page showing the batch's complete history — and every stage on that page is independently re-checked against a blockchain record at the moment the page loads, not just read out of a database that could, in principle, be edited.

The build follows one discipline throughout: Postgres holds the real data, the chain holds only enough to prove it hasn't been tampered with. That split is the whole point of the architecture below.

01

Architecture & trust boundary

Three independently-replaceable layers: Flutter renders every screen for every role and knows nothing about the chain. Django + GraphQL is the only source of truth for "what happened" and the only thing that can write to the chain, via a service-owned relayer wallet. Solidity stores nothing but batch IDs, event types, and content hashes — an append-only ledger that exists purely to let anyone catch tampering after the fact.

03

Data model & the trust mechanism

Seven models, kept deliberately flat: User (role: beekeeper or admin — a consumer is never a row, just an anonymous visitor), Apiary, Hive, HoneyBatch, QualityCheck, Package, and the one that matters most:

BatchEvent — the spine of the whole system

Every stage transition creates exactly one row: batch, event type, actor, timestamp, a JSON payload, and three chain-facing fields — data_hash, tx_hash, chain_event_index. That last one matters more than it looks: it's what lets the trace page ask the contract "does event #2 of batch HC-2026-0001 still hash to this exact value?" instead of guessing from array position.

# backend/traceability/services/hashing.py — computed ONCE per event
canonical = json.dumps({"batch_id", "event_type", "event_data"}, sort_keys=True)
data_hash = "0x" + keccak256(canonical)

# that single hash is then written to BOTH places, in the same call chain:
BatchEvent.objects.create(..., data_hash=data_hash)   # → Postgres
contract.recordEvent(batch_id, event_type, data_hash)  # → chain

Because both copies come from one computation, they cannot silently drift apart. If anyone edited a BatchEvent row directly in Postgres afterward, recomputing its hash would no longer match what's on-chain — and the public trace page checks that live, for every event, on every page load, by calling the contract's verifyHash().

04

The workflow

A HoneyBatch is a small state machine. Beekeepers own the first two stages (their own fieldwork); admins own the approval and release gates — matching the spec's role split, and keeping the one golden path unambiguous.

05

Who can do what

Beekeeper
  • Register & manage apiaries
  • Register & manage hives
  • Create honey batches from a harvest
  • Record processing
  • View full history of their own batches
Admin
  • View every beekeeper, apiary, hive, batch
  • Record & approve quality checks
  • Package a batch (mints the QR)
  • View blockchain transaction info per event
Consumer
  • No account, no login, no wallet
  • Scan / open a batch's QR code
  • See the complete, dated event history
  • See a live verified/not-verified badge per stage

07

Engineering decisions

Why a local Hardhat node instead of a public testnet?
It's a real EVM implementation, so nothing about the contract or the integration changes for a public chain later — but a hackathon demo shouldn't depend on faucet uptime, a funded wallet, or network latency during judging. Swapping to Sepolia or Polygon Amoy is exactly three env vars: WEB3_RPC_URL, RELAYER_PRIVATE_KEY, and redeploying the contract.
Why does the backend hold the private key?
The spec is explicit: no user should need a wallet or real cryptocurrency. One relayer address, allowlisted in the contract's constructor, signs every transaction server-side. It's a known, accepted limitation for an MVP (single-writer nonce management, not a production multi-node design) — called out rather than hidden.
Why hand-written GraphQL types instead of an auto-CRUD layer?
Strawberry supports Django auto-generation, but this schema is small and the mapping from model to type isn't 1:1 everywhere (the public trace type computes live verification per event). Hand-writing kept every field's intent explicit.
What was deliberately left out?
IoT sensors, AI, disease detection, predictive analytics, a marketplace, payments, NFTs, token economics, GPS tracking, and a custom blockchain — all explicitly out of scope for this MVP, in favor of one complete, working, end-to-end flow.
